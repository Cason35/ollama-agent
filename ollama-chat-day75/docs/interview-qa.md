# Agent Platform Interview Q&A（30 组）

### 1. 为什么 Agent 需要 Workflow？
Agent 擅长动态决策，Workflow 擅长确定依赖、状态和恢复。本项目让简单任务直接执行，复杂任务进入 DAG，避免自由循环不可控。备选是纯 Agent 或硬编码流水线；代价是维护两类执行路径，收益是灵活性与可靠性兼得。

### 2. 为什么使用 DAG？
DAG 能显式表达依赖和并行，并在运行前检测环。线性 Pipeline 不适合分支，自由图难以终止；代价是节点必须清晰定义输入输出。

### 3. 为什么需要 Durable Execution？
模型和工具任务耗时且昂贵，进程故障后全量重跑会浪费成本。项目在节点边界保存 Checkpoint，支持 Resume / Replay；代价是状态版本和幂等设计更复杂。

### 4. 如何避免恢复时重复副作用？
节点使用稳定 Run ID 与 Idempotency Key，先检查持久状态再调用外部工具；不可幂等操作需要补偿。仅靠队列“至少一次”不能解决业务重复。

### 5. 为什么 Agent 需要 Memory？
上下文窗口不是可靠持久层。Session Memory 保持当次连贯，Long-Term Memory 保存经过抽取与治理的偏好和经验；代价是错误记忆和隐私风险，因此需要来源、置信度、过期与删除。

### 6. Memory 与 RAG 有何不同？
Memory 以用户和交互经验为中心，RAG 以外部知识证据为中心。两者都检索，但权限、更新、可信度和生命周期不同，本项目分服务实现并在 Runtime Context 合并。

### 7. 为什么 RAG 需要 Rerank？
初始召回优化覆盖率，不一定优化最终相关性。项目以 Hybrid Search 扩大候选，再用多信号重排提升引用质量；代价是额外延迟，因此保留降级路径。

### 8. 如何保证 Citation 可信？
每个候选携带文档、Chunk、索引版本和租户元数据，生成后验证引用是否来自提供的证据。模型给出的裸 URL 不直接视为可信引用。

### 9. 为什么需要 Index Version？
知识变化会让同一查询结果漂移。记录索引版本可以复现评估、灰度新索引和安全回滚；代价是存储与生命周期管理增加。

### 10. 为什么 MySQL 与 Vector Store 分开？
MySQL 适合事务和结构化事实，Vector Store 适合近邻搜索。分工提高专业性但带来一致性问题，因此 MySQL 是事实源，索引允许重建。

### 11. 为什么使用 Redis Queue？
Redis 延迟低、开发环境易部署，并可复用缓存和锁基础设施。相较 Kafka 运维更轻，但持久性和超大规模能力较弱，所以任务状态不能只存在 Redis。

### 12. 如何处理 Redis 故障？
健康检查和 Worker 暂停接收新任务，持久任务状态不丢失；恢复后依据 Checkpoint 重投未完成任务。项目提供故障脚本，但生产结论必须经过真实演练。

### 13. Runtime Context 解决什么问题？
它统一携带 Tenant、User、Trace、Permission 与 Budget，避免每层散乱传参或重新读取身份。代价是需要控制大小，并为后台任务序列化最小快照。

### 14. 如何实现多租户隔离？
API Gateway 先鉴权，Runtime Context 固定 Tenant ID，存储查询和 Redis Key 再按租户过滤，越权默认拒绝并审计。只在前端隐藏不构成安全隔离。

### 15. RBAC 是否足够？
不够。RBAC 管角色权限，资源所有权、Tenant、Quota 和具体动作仍需策略校验。本项目的 Permission Service 在资源访问前综合判断。

### 16. 为什么需要 Quota？
模型调用昂贵且易被滥用。按租户和用户限制请求、Token、工具与并发可控制成本；硬限制可能影响关键任务，因此需要分层阈值和审计例外。

### 17. 为什么 Evaluation 不能只看人工感觉？
主观抽查不可重复，也难发现回归。项目用固定数据集、指标、Baseline、Bad Case 与 Quality Gate；人工评审仍用于校准指标无法覆盖的价值判断。

### 18. Quality Gate 如何设置？
同时检查最低质量、引用准确率、回归幅度与安全项，严重安全失败直接阻断。阈值应来自业务风险和历史分布，而不是任意追求高分。

### 19. Prompt 如何发布？
Prompt 有不可变版本，经离线评估和实验后 Promote；运行记录绑定版本。直接覆盖文本虽然简单，但无法复现和回滚。

### 20. 如何选择模型？
Model Router 按任务能力、延迟、成本、健康和预算路由，并用 Circuit Breaker 隔离故障。单模型更简单，但会形成可用性和成本单点。

### 21. Multi-Agent 什么时候值得用？
当任务能按专业角色分解、并行收益明显且结果可验证时值得使用。简单问答使用多个 Agent 只会放大延迟、成本和协调错误。

### 22. 多 Agent 冲突如何处理？
保留各自证据与置信度，由 Merge 策略按证据、规则或 Supervisor 裁决；无法消解时显式展示分歧。不能用最后一次输出静默覆盖。

### 23. 如何做可观测性？
Trace ID 关联请求、Agent、节点、模型、工具、日志、指标、错误和评估。日志回答发生了什么，Metric 看趋势，Trace 看因果路径，三者不能互相替代。

### 24. 如何防止日志泄密？
入口和输出统一 Masking，默认不记录密钥、完整 Prompt、个人数据或 Token；关键字段使用引用或哈希。生产还需采样审查和保留策略。

### 25. 为什么需要 Feature Flag？
它把部署与功能启用解耦，可缩小故障半径。项目用稳定哈希保证同一主体灰度一致；代价是过期 Flag 会增加认知负担，因此需要所有者和清理日期。

### 26. 为什么采用模块化单体？
当前教学与作品集规模下，它简化本地运行、事务和调试，同时保留清晰领域边界。微服务会过早引入网络与运维成本；规模增长后可沿 Queue、RAG 等边界拆分。

### 27. 数据库 Migration 如何安全发布？
迁移按版本排序且可重复检查，先备份，再采用向后兼容的 expand / migrate / contract 流程，并准备回滚或恢复。破坏性 Schema 修改不能和应用切换同时赌博。

### 28. Backup 等于灾难恢复吗？
不等于。Backup 只有通过定期 Restore、校验完整性并达到 RPO / RTO 才形成恢复能力。本项目提供脚本，真实生产仍需跨故障域演练。

### 29. Benchmark 如何避免失真？
固定代码、模型、数据、参数、硬件和缓存状态，执行多轮并保存原始结果；区分代码层、模拟与真实环境。本项目不为未执行的完整环境测试编造数字。

### 30. v1.0.0 的最大工程价值是什么？
不是功能数量，而是从 Runtime Context、持久工作流、RAG 引用、评估回归、可观测治理到生产交付形成闭环，并用 README、ADR、Demo、Benchmark 和安全记录让他人可以理解、验证和维护。
